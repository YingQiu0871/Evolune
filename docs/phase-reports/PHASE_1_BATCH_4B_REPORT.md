# Evolune Phase 1 Batch 4B Report

Date: 2026-08-04

## 1. Scope

Batch 4B adds an instrumentation migration matrix for the existing Room v2 to v3 migration. It validates legal and illegal legacy values, transaction rollback, slot backfill, foreign keys and indices, the authorized v1 to v2 to v3 chain, a fixed-seed long-history fixture, and deterministic replay.

This batch does not change the production migration, Room entities, repositories, JSON, PK behavior, UI, reminders, widgets, Wear code, Gradle configuration, the manifest, or either Room schema file. Batch 3C and Batch 4C have not started. Room v3 remains an internal, non-releasable schema.

## 2. Added files

- `app/src/androidTest/java/io/github/yuninggu/evolune/data/AppDatabaseMigrationMatrixTest.kt`
- `docs/phase-reports/PHASE_1_BATCH_4B_REPORT.md`

The matrix contains 22 device tests and only synthetic identifiers and values. No real, anonymized-from-real, or real-derived health data is present.

## 3. Legal timeH matrix

The matrix verifies all values in a single migration and compares them with independently fixed expected epoch-millisecond values:

- epoch zero;
- ordinary positive and negative values;
- a millisecond-precision value mapping to `1700000000123`;
- positive and negative `Math.round` boundary values represented by fixed IEEE-754 literals;
- legal values close to the positive and negative `Long` limits;
- multiple events migrated together;
- exact preservation of every legacy `timeH` value.

Expected epoch values are constants in the test and are not generated by the production migration helper under test.

## 4. Storage classes, Infinity, and overflow

Actual Android SQLite behavior was verified before migration reads numeric values:

- ordinary floating-point bindings are stored as SQLite `real` and migrate successfully;
- an integer binding into the exact v2 `REAL NOT NULL` column is normalized by SQLite affinity to `real`, then migrates successfully;
- `TEXT` and `BLOB` storage are materialized, rejected by migration preflight, and fully rolled back;
- positive and negative Infinity are rejected and fully rolled back;
- positive and negative epoch-range overflow values are rejected and fully rolled back;
- positive and negative multiplication-overflow values are rejected and fully rolled back.

The exact v2 schema cannot materialize `NULL` because `timeH` is `NOT NULL`. Android SQLite also binds `NaN` as `NULL`, so the same constraint rejects it before migration. These are recorded platform/schema fixture limits rather than fabricated database states. The pure JVM migration primitive tests continue to cover `NULL` storage policy and `NaN` conversion policy directly.

## 5. Rollback matrix

Independent tests cover:

- non-minute plan time;
- malformed JSON;
- a non-string JSON element;
- invalid `LocalTime`;
- positive and negative Infinity;
- positive and negative range overflow;
- positive and negative multiplication overflow;
- `TEXT` and `BLOB` `timeH` storage.

After every migration failure, a version-2 raw helper verifies:

- `PRAGMA user_version = 2`;
- the seven v3 event columns do not exist;
- `scheduled_dose_slots` does not exist;
- neither slot index exists;
- `room_master_table` retains the v2 identity hash;
- all legacy event rows and storage representations are unchanged;
- all plan rows and original `timeOfDay` strings are unchanged;
- no partial update or insert remains.

A valid v2 fixture cannot construct a slot insertion conflict during backfill: plan IDs are primary keys, parser positions are contiguous and unique, and Slot ID v1 includes plan ID, position, and canonical local time. The v3 unique constraint is therefore exercised independently after migration.

## 6. Plans and slots

The plan matrix covers multiple plans, multiple slots, empty string and empty-array plans, duplicate times, equal positions in different plans, `00:00`, `23:59`, and `08:30:00` canonicalized to `08:30`.

It verifies that:

- original `timeOfDay` strings remain byte-for-byte unchanged;
- each slot references its source plan;
- positions start at zero and remain contiguous;
- list order is preserved without sorting or deduplication;
- duplicate local times remain distinct by position;
- every Slot ID matches an independent UUIDv5 implementation;
- the total slot count equals the total parsed input count.

## 7. Foreign keys, indices, cascade, and uniqueness

The matrix verifies:

- `PRAGMA foreign_keys = 1` through a production Room open;
- orphan insertion is rejected;
- deleting one plan cascades only that plan's slots;
- another plan's slots remain intact;
- `(planId, position)` is unique;
- equal positions are legal across different plans;
- different positions are legal within one plan;
- the ordinary `planId` index exists;
- the unique index column order is `planId`, then `position`;
- no unique index exists on `localTime`;
- `PRAGMA foreign_key_check` is empty.

## 8. v1 to v2 to v3 chain

The repository has no trusted Room `1.json`. The test therefore does not invent one. It creates only the minimal v1 `dose_events` SQL fixture authorized by the design and historical migration precondition, then opens the real production `AppDatabase` so its private registered `MIGRATION_1_2` and current `MIGRATION_2_3` execute in sequence.

The chain reaches `user_version = 3`, preserves the legacy event, derives the expected epoch milliseconds, creates the plan and slot tables, and records the current v3 Room identity.

## 9. Fixed-seed long history

The deterministic stress fixture uses fixed seed `0x4B4B2026` and contains:

- 2,000 synthetic events;
- 100 synthetic plans;
- 267 total slots, with zero to five slots per plan;
- minute-precision slot times including duplicates;
- positive and negative `timeH` values;
- a legitimate epoch-zero event.

It verifies every event conversion, every legacy `timeH`, every original `timeOfDay`, every slot position, every independent UUIDv5 result, all row counts, and the absence of orphan rows. Device-observed migration durations were 147 ms in the target run and 143 ms in the subsequent full connected run. No strict timing assertion is used.

## 10. Deterministic replay

The same fixed-seed synthetic fixture is created in two independent v2 databases and migrated separately. The test compares all event v3 fields, all slot IDs and ordering, slot counts, Room identity, explicit indices, and foreign-key metadata. Results are identical. `MIGRATION_2_3` is not rerun on the same database.
