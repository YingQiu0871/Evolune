# v1.7-B-02 incidental repair — instrumentation test isolation

## Summary

The full Phone instrumentation suite failed deterministically with three failures while this round
was being verified. The failures were **not** caused by B-02 production code. They are a
pre-existing test-isolation defect: one test class closes the production Room database without
dropping the process-wide repository-provider handle to it, so every later test that uses
`ProductionRepositoryProvider.get(...)` receives a *closed* database.

The round fixes that defect (test code only) so the affected-surface verification can be executed on
a green suite. No production file is touched by the repair.

## Evidence chain

### 1. Room cancels its coroutine scope when a database is closed

`androidx.room.RoomDatabase` (room-runtime 2.8.4) creates the scope and cancels it on close:

```
private kotlinx.coroutines.CoroutineScope coroutineScope;
  140: invokestatic  SupervisorKt.SupervisorJob:(...)      // scope = CoroutineScope(SupervisorJob() + ...)
public void close();
   4: invokevirtual  CloseBarrier.close$room_runtime:()V
private final void onClosed();
  19: invokestatic  CoroutineScopeKt.cancel$default:(...)  // coroutineScope.cancel()
```

Any suspend DAO call made through a closed database therefore fails with the cancelled
`SupervisorJob` as `JobCancellationException` instead of a storage error.

### 2. The production database and provider already exist before the first test

Temporary diagnostic probes were added to the instrumentation suite for one run (they only *read*
static state; they were deleted again before the round was closed). Device logcat:

### 3. What creates the provider before the tests: a package-scoped BOOT_COMPLETED

The app is freshly installed at the start of every UTP run, and Android delivers a package-scoped
`BOOT_COMPLETED` to a newly installed app:


`ProductionRepositoryProvider.get` / `AppDatabase.getDatabase` recorded the call site:

So the receiver creates the database + provider on a background thread in the same process, roughly
1.5 s after install and long before `AppDatabaseMigrationMatrixTest` runs.

### 4. Why only these two classes failed

`AppDatabaseMigrationMatrixTest` (`@Before`/`@After` of every one of its 22 methods) closes the
production database and nulls `AppDatabase.INSTANCE` — but it did not clear
`ProductionRepositoryProvider.instance`. Every later `ProductionRepositoryProvider.get(...)` call
therefore returned the stale provider. Tests that assert real production data
(`HistoryReadZeroWriteDeviceTest`, `HistoryRefreshDeviceTest`) failed; tests that only assert
persisted UI state passed, because a failed read is reported as ViewModel error state.

## Repair (test code only)

`AppDatabaseMigrationMatrixTest.resetProductionDatabaseSingleton()` now drops **both** process-wide
handles — it closes `AppDatabase.INSTANCE` exactly as before and additionally nulls
`ProductionRepositoryProvider.instance`, with a KDoc explaining the broadcast path that can create
the provider before the test runs.

```
private fun resetProductionDatabaseSingleton() {
    val instanceField = AppDatabase::class.java.getDeclaredField("INSTANCE")
    instanceField.isAccessible = true
    (instanceField.get(null) as? AppDatabase)?.close()
    instanceField.set(null, null)

    val providerField = ProductionRepositoryProvider::class.java.getDeclaredField("instance")
    providerField.isAccessible = true
    providerField.set(null, null)
}
```

| after repair (full Phone) | `:app:connectedDebugAndroidTest` | 247 | 5 | 0 |

Both before and after runs used the same emulator (Pixel_7 AVD, API 35), the same test order, and the
same frozen set of earlier-round evidence.

## Residual risk / follow-up

- The production provider has no self-healing path: if anything ever closes the production database
  while the process keeps running, `get()` keeps returning the closed handle. No production code path
  closes it today (`RoomRestorePersistence` replaces rows inside a transaction instead of closing the
  database), so this stays a test-hygiene property rather than a product defect.
- The receiver-triggered creation is legitimate product behaviour (restoring reminder alarms after an
  app update or install). Test suites that reset process-wide singletons must reset all of them.
