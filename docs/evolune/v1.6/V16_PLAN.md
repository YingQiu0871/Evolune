# Evolune v1.6 — Widget Gallery 分步实施方案

状态：`DONE / RELEASED AS v1.6.0`。2026-09-05 建立，2026-09-10 完成 A–G、独立复审、真实设备验收和发布封版。
规划时工作树为 `main`，HEAD 为 `df12329`（v1.5 最终发布验收收口）。
实施基线以 A 阶段记录的 `v1.5.0` tag、实际起点提交和已有本地变更为准。

## 版本目标与交付范围

让用户按查看目的选择手机 Widget、Wear Tile 和表盘信息；各入口对同一次服药、
同一时刻的 E2 估算和今日进度给出一致结果，继续由 Phone Room/domain/repository 提供权威数据。

本方案将路线图候选拆为以下交付目标。每个阶段独立审阅，全部必交付项通过后才进入发布。

| 编号 | 目标 | 交付与完成标准 |
|---|---|---|
| A | 冻结基线与产品规格 | 样式、尺寸、状态、交互和性能预算可逐项验收 |
| B | 统一展示与配置契约 | 新旧样式复用语义；配置按实例隔离；缺失字段有明确兼容方案 |
| C | 手机常用样式 | 今日计划、下一次服药、今日进度、当前 E2、PK 图表五种可选样式可用 |
| D | 手机 PK 图表 | 大尺寸只读曲线，数值与现有 PK 结果一致，刷新开销受控 |
| E | Wear Tile | 下一次服药、今日待服、当前 E2 三种 Tile 可用，现有 Tile 保持可用 |
| F | 表盘信息 | 下一次服药时间、当前 E2、今日完成度三种 Complication 可选 |
| G | 集成与发布验收 | 升级、跨端一致性、真实宿主、后台表现和发布包验收闭环 |

范围调整必须在实施前写明受影响目标和原因。不能把未完成的必交付项直接标为通过；
需要延期时，由项目负责人决定并同步本表、路线图与验收记录。

## 现有基础与已知缺口

- 手机 `WidgetPresentation.kt` 已包含 occurrence 时间线、今日完成数和语义时间边界；
  `WidgetWork.kt` 已有共享快照加载、批量刷新及确认动作，`WidgetAppearance.kt` 按
  `appWidgetId` 保存主题、颜色与透明度。优先扩展这些入口，不另建用药状态存储。
- 当前 `WidgetSnapshot` 提供浓度标量，尚不能直接满足新样式的计算时间、趋势和完整曲线需求。
  D 阶段需要复用 PK 引擎生成有界展示数据，不能把单个数值伪装成趋势。
- 旧 `DoseTileService` 使用 `WearPlanStore` 与 `/hrt/dose-actions`；Wear App 使用独立的
  版本化 snapshot/confirmation 路径。新增 Tile 的动作必须基于明确 occurrence，
  不能直接把旧 Tile 的 planId 动作接到“下一次服药”按钮上。
- `WearAppProtocol.kt` 的现有快照提供最近记录、有限的 upcoming occurrences 和 E2 状态，
  不足以直接推导完整今日计划及今日完成度。今日汇总应由 Phone 生成；不能把前几个待办当分母。
- 当前 Wear manifest 已保留已有 Dose Tile，并注册三种候选 Tile 与三种 SHORT_TEXT Complication provider；真实表盘槽位和后台刷新仍需宿主集成验证。

## 实施顺序

按 A → B → C → D → E → F → G 推进，每阶段使用独立提交或 PR。
B 完成手机共享契约后，Wear 协议扩展可单独审阅；E/F 必须等待其通过。
每阶段先完成可审阅成果，再进入该阶段审阅；问题修复后复核受影响范围。

### A — 基线、样式规格与验收预算

1. 记录 v1.5.0 tag、开发起点、Phone/Wear 版本、设备/API、launcher 和测试表盘。
   保留 v1.5 已有验收结论及豁免的原始含义，不把耗电豁免继承为 v1.6 测试通过。
2. 盘点现有 Widget、旧 Tile、Wear App 的字段、状态、动作、刷新触发与测试入口。
3. 为各样式画出正常、无计划、无记录、全部完成、数据过期、错误等状态稿。
   Phone 先以 2×2 紧凑、4×2 横向、4×3 图表为设计目标；实际最小 dp 和缩放断点
   经宿主验证后冻结，不能假定不同 launcher 的网格等大。
4. 冻结“下一次”选择规则、可确认动作边界、今日统计时区/分母、过期阈值、E2 趋势时间窗、
   图表时间窗与采样上限。Phone Gallery 显示可以包含未来 occurrence，但只有现有
   `MedicationActionAvailability.AVAILABLE` 且日期检查通过时才显示确认，点击时 action handler 还必须
   重新验证同一 availability、occurrence identity、本地日期和计划状态；Wear App 和新 Wear Tile
   明确保留现有 v1.3 的 `UPCOMING`/`DUE` occurrence confirmation 兼容语义，仍必须等待 Phone
   持久化回执。零分母显示“今日无计划”，不显示虚假的 100%。
5. 用 v1.5 的 PK-EMPTY/STEADY/DENSE 固定数据建立 1、3、5 个 Widget 和多个 Wear 展示面的
   刷新基线。冻结耗时、PK 调用数、Data Layer 请求数及后台唤醒预算，并说明测量方法。

交付：`V16_SPEC.md`（实施时建立，含状态/尺寸/动作/预算表）及基线证据。
审阅：产品视觉与可读性审阅、数据契约审阅；规格仍有未定语义或预算时，A 不关闭。

### B — 共享展示状态、实例配置与兼容契约

1. 基于现有 mapper/loader 定义样式所需的派生字段；保留明确的计算时间、数据状态和单位。
   一个刷新批次共享可复用的数据加载/计算，不因实例数增加而逐个重复完整 PK 运算。
2. 扩展现有按实例配置：增加稳定样式标识，沿用主题/配色/透明度。
   默认方案是在现有配置页选择样式并预览；A 阶段确认系统选择器是否需要独立入口。
3. 旧配置缺少样式字段时保留原有组合布局；覆盖未知值回退、取消不保存、删除清理、
   重新配置、实例 ID 恢复映射与多个实例互不污染。保留原有 provider 身份，保证升级存量 Widget。
4. 列出 Wear 字段缺口，为今日计划/进度定义 Phone 派生汇总、日期、时区、计算时间与截断标识。
   必要的协议扩展独立成提交，先完成编码、解码、版本协商及新旧 Phone/Watch 配对设计。
   缺字段显示不可用，不能默认为零；未审阅通过前不更改线上 payload。
5. 对共享语义、配置兼容及协议边界补确定性测试，保留原有确认/撤销权威路径。

交付：共享状态与配置代码、协议设计/兼容矩阵、对应测试。
审阅：重点验证事实来源、数据完整性、旧版本兼容和批量刷新成本；B 通过才接新 UI。

### C — 手机四种常用样式

1. 在配置页加入样式选择和与实际样式对应的预览，串通添加、取消、保存、再次配置流程。
2. 依次实现今日计划 → 下一次服药 → 今日进度 → 当前 E2。
   今日计划显示不下时明确“更多”并进入应用；当前 E2 显示估算单位、计算时间和有效趋势。
3. 快速确认复用现有 occurrence 动作：只对 `AVAILABLE` occurrence 显示动作，且在点击时重新验证
   `AVAILABLE`、occurrence identity、本地日期和计划状态；旧/stale PendingIntent、渲染后过期、同日
   `UPCOMING`、已删/已改方案和写入失败均不得落库或先显示成功。
   `UPCOMING`/跨日未来 occurrence 只读并进入应用；重复点击只写一条，写入成功后更新各入口。
   B 阶段已补上该 action-time 门槛及确定性测试；C 阶段必须在新样式接入时保持同一双重校验，不能由 UI 绕过。
4. 完成各尺寸、长药名、大字体、深浅色、对比度、12/24 小时制及无障碍描述。
5. 在至少两个实际 launcher 宿主验证添加、缩放、拖动、重配、多实例、升级保留和删除。

交付：四种可选样式、兼容默认布局、截图与操作证据、动作回归结果。
审阅：界面实测与数据/动作审阅分别给结论；预览截图不能替代真实宿主验收。

### D — 手机大尺寸 PK 图表

1. 复用现有 PK 引擎、事件适配和单位，按 A 冻结的时间窗及采样上限生成图表数据。
2. 实现时间轴、浓度单位、当前时间标记、计算时间和无数据/过期状态；点击进入应用图表。
   图表保持只读，不增加 Widget 内缩放、拖动或用药编辑。
3. 对不同历史长度、给药途径及固定时钟，比较曲线采样值与现有引擎结果；
   展示降采样不能改动 PK 模型或计算参数。
4. 验证缩放后的标签/曲线、缓存失效、体重/记录变更、跨午夜与时区变化。
5. 重测 EMPTY/STEADY/DENSE 及多实例成本；仅有数值卡片时不触发完整图表计算。

交付：图表样式、数值一致性结果、宿主截图及与预算对照的性能记录。
审阅：数值回归、视觉可读性和运行成本三项均通过。

### E — 三种 Wear Tile

1. 先接入 B 审阅通过的共享快照/派生状态；按当前 E2 → 下一次服药 → 今日计划顺序实现。
2. 保留现有 Tile service 身份和用户已添加的 Tile。新增样式共用数据获取与刷新协调，
   不为每个 Tile 建一条常驻轮询链。
3. 下一次服药的确认复用 Wear App 的 occurrence confirmation 与 Phone 回执，保留其已冻结的
   `UPCOMING`/`DUE` 兼容语义；这不把 Wear 规则反向套到 Phone Gallery。明确区分已发送、待处理、
   已记录、失败，只有收到持久化成功结果才标记完成。若未来改为 `AVAILABLE`，必须先扩展版本化
   snapshot/action contract 并完成旧/新组合矩阵。
4. 今日计划显示范围和截断必须清楚；完整统计来自 Phone，不由截断列表推算。
5. 验证断连、过期、乱序快照、重试、重复点击、Phone 恢复后 producer 变化、
   进程重建和重启；在圆形真表验证文字、触控和 Tile 切换。

交付：三种 Tile、旧 Tile 兼容证据、跨端操作与断连矩阵。
审阅：协议/动作与真表交互分别审阅，关注误记、假成功和旧状态覆盖新状态。

### F — 三种表盘信息

1. 根据当前工程依赖及官方接口确认可支持的数据类型和宿主，记录于规格；
   为下一次服药时间、当前 E2、今日完成度提供相应 provider、标签和选择器预览。
2. 复用 E 的共享快照；点击进入相应 Wear App 页面，不直接从表盘触发写入。
3. 窄区域优先保留数值含义、单位和状态；不可用/过期时使用明确占位，
   无障碍说明提供完整信息，防止把旧估算显示成当前有效值。
4. 覆盖表盘添加/替换、不同槽位、环境模式、断连、跨日、重启和多 provider 更新合并。
5. 用真实兼容表盘及至少另一种槽位/布局验证；测量多展示面同时启用的后台成本。

交付：三种 provider、支持类型清单、真实表盘证据及后台测量。
审阅：宿主生命周期、信息准确性、可读性和刷新预算；仅能编译不能关闭此阶段。

### G — 集成、升级与发布验收

1. 从已发布 v1.5.0 做覆盖升级，检查原 Widget/Tile、配置、记录、提醒、备份与 Wear App。
2. 固定同一数据和时钟，比较 Phone App、各 Widget、Wear App、Tile、Complication；
   日期/完成度/浓度须符合相同契约，允许的展示延迟必须与时间戳和过期规则一致。
3. 执行审阅文档中的设备/异常/性能矩阵；关闭全部阻塞问题，回归修复触及的链路。
4. 在候选提交完成构建、自动化、真机和签名安装验证；更新功能矩阵、用户说明与发布说明。
5. 单独进行发布审阅，记录确切提交、Phone/Wear 包身份与产物；通过后按项目发布流程封版。

交付：完整 `V16_ACCEPTANCE.md`、独立审阅结论和发布候选证据。
审阅：按 [V16_REVIEW.md](V16_REVIEW.md) 的 G 门槛决定是否允许发布。

## 全程边界

- 不改 E2 模型、Room schema、备份格式、签名或应用身份；必要的新展示字段只作为派生数据。
- 不加入 CPA、个性化 PK、云实时同步或新的健康权限；CPA 仍属于 v1.7。
- 不新增独立权威事实来源；允许复用可重建的 Wear 派生 snapshot/cache，但不得绕过持久化成功、
  稳定 identity、幂等及冲突处理。
- 不为了显示“当前”而添加每秒后台刷新；在系统允许的刷新能力内展示时间与有效性。
- 仅抽取本批次确有复用的逻辑，不预先做通用框架或大规模重构。

审阅规则与证据模板见 [V16_REVIEW.md](V16_REVIEW.md)。
