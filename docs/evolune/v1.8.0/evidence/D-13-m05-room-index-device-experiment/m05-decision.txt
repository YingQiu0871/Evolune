EVOLUNE v1.8.0 D-13 — M05 DECISION
==================================

Question (charter §3): at realistic supported data cardinalities, do the
existing unindexed dose-event queries create enough Android Room/SQLite cost
to justify a shipped schema/index migration? If candidate indexes improve
reads, is the benefit large enough to justify their write/restore/migration
cost and schema risk?

Measured answers (Pixel_7 AVD, Android 15 / API 35, Room 2.8.4, SQLite 3.44.3,
journal=WAL; 30 timed reps per cell, 5 warm-ups; deterministic 5%
null-localDate fixtures):

1. Plan shape: the audit's SCAN + temp B-tree shape reproduces on-device for
   all seven time/date queries at baseline (query-plan-baseline.txt). The
   candidate indexes do eliminate scans/sorts where designed
   (query-plan-indexed.txt). The plan-shape part of M05 is real.

2. But the measured COST of that plan shape is already small at realistic
   cardinalities:
     - 100 rows  (~1-3 months of use): worst median 0.57 ms, worst p95 0.68 ms
     - 1000 rows (~1-3 years of use):  worst median 0.78 ms, worst p95 0.81 ms
     - recent-20 median 0.15-0.30 ms; all-history median 0.17-0.18 ms
   Even the 10,000-row STRESS fixture stays at median <= 1.73 ms /
   p95 <= 2.90 ms. 10k is beyond plausible use for a dose tracker and does
   not decide this alone (charter §8/§20).

3. The candidate indexes DO improve reads — by 0.02-0.35 ms per query at
   representative cardinalities (up to ~60% relative, on an already
   sub-millisecond base), and up to 1.6 ms absolute at 10k stress
   (read-latency-comparison.txt). These queries run on Room's executor;
   they are not Main-thread blocks (no-main-thread-conflation.txt), and the
   dominant per-load cost is the 40-150 ms projection CPU already off-Main
   (D-09/D-10, M02 CLOSED). A 5 ms-scale saving does not exist here; the
   entire query stage is a fraction of one already-async load.

4. The costs of shipping are measured, not assumed:
     - bulk insert +21-22% at 1k/10k rows (37→45 ms, 382→461 ms);
     - restore-like replace +12%/+0.5%/+3.7% at 100/1k/10k;
     - per-event single-write medians +0.01-0.03 ms on EVERY recorded dose,
       edit, Wear confirmation, and restore row;
     - database file +33%/+66%/+84% (≈ +135 KB at 1k rows);
     - schema identity work: version bump + migration + exported-schema
       update + restore/upgrade compatibility — rated HIGH risk by the
       authoritative audit (M05 finding: "Risk/tests: HIGH for any shipped
       index: migration/version identity, restore, upgrade and write cost").

5. Index-build/migration-creation time is trivial (<=2 ms at 1k rows;
   <=25 ms at 10k) and therefore neither supports nor blocks the decision
   (index-build-migration-relevance.txt).

6. SET C3 (direction-specific third index for recent-20) is explicitly
   evaluated and REJECTED by the evidence: it removes the residual partial
   sort but buys <= 0.007 ms over SET B at 10k and is slower than B at 1k,
   while adding a third index's write/storage cost. No index is added merely
   to make every EXPLAIN line index-backed.

Synthesis against the charter's §20 framework:
- Realistic cardinalities show baseline query latency is already small
  (sub-millisecond; sub-2 ms even at implausible stress). ✓ (A-condition 1)
- Meaningful relative index benefit exists at all sizes, but the ABSOLUTE
  read gain at realistic scale is 0.02-0.35 ms per already-async query. ✓
  (A-condition 2: no material user-visible benefit)
- Read gains do not justify the measured write/restore/storage cost and the
  HIGH-risk schema/migration identity work. ✓ (A-condition 3)

The exact candidate index set supported by the evidence, should a future
slice ever revisit this (NOT authorized by D-13): SET C =
  (localDate, occurredAtEpochMillis, id) + (occurredAtEpochMillis, id)
— with the direction-specific third index explicitly rejected.

M05 classification: A — M05 CLOSED / NO INDEX IMPLEMENTATION JUSTIFIED.
No schema commit follows; no migration slice is proposed.

No invented millisecond SLA is used: the decision weighs absolute latency,
p95, production cardinality, trigger frequency, measured index gain,
measured write cost, measured storage growth, trivial build cost, and the
audit's HIGH schema-risk rating together (charter §21).
